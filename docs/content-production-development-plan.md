# GEOFlow 内容生产后续开发计划

## 1. 文档目的

本文将《GEOFlow 内容生产改造方案》转化为可执行的开发顺序、交付边界和验收标准。

本计划只覆盖 GEOFlow 内部改造，不包含 seo-diagnostic 对接。两个项目先独立演进，后续再通过稳定接口连接。

## 2. 开发目标

第一阶段的核心结果不是一次性复制全部竞品功能，而是建立一条可靠、可观察、可恢复的内容生产主链路：

> 选题 → 研究证据 → 内容简报 → 标题与大纲 → 分段写作 → 组装 → 质量检查 → 定向修复 → 人工审核 → WordPress 发布 → 多平台改写

### 迭代 21A：AI 内容策划

目标：把标题与大纲从固定模板升级为基于当前主题、已确认简报和证据摘要的 AI 辅助决策，同时不改变人工确认与版本不可静默覆盖的约束。

交付：

- 标题候选优先调用当前启用的非 Embedding 写作模型，输出简体中文标题及选择理由；
- 大纲候选优先调用写作模型，生成两个可比较的 H2/H3 结构，并自动关联简报中的证据；
- 页面明确显示“AI 生成”或“规则生成”，不把降级结果伪装成 AI 结果；
- 发生模型配置、接口或结构化输出错误时继续保留可用的规则兜底，管理员修复模型后可以重新生成；
- 所有结果仍通过既有方向版本保存、确认和下游失效机制处理。

验收：

- 已配置可用写作模型时，标题和大纲与内容简报、证据摘要保持一致；
- 未配置或模型失败时，流程不中断，页面清楚提示规则生成；
- 手工选择、编辑或确认后，已有章节和发布流程仍按既有失效规则执行。

系统需要同时支持：

- 全程简体中文输出；
- 使用企业知识库、URL 导入资料和可信外部来源；
- 每个阶段可查看、重试、回退和人工调整；
- 自动任务与人工向导共用同一条生产管线；
- WordPress 主文章与多平台版本保持内容归属关系；
- 失败可恢复，重复执行不会重复发布；
- 保留现有生成链路作为回退路径，逐步迁移。

## 3. 当前基础与复用原则

### 3.1 可直接复用的现有能力

| 能力 | 当前基础 | 后续定位 |
| --- | --- | --- |
| 文章与任务 | `Article`、`Task`、`TaskRun`、`TaskSchedule` | 保留，作为内容结果和调度入口 |
| 知识检索 | `KnowledgeBase`、`KnowledgeChunk`、`KnowledgeRetrievalService` | 作为研究阶段的内部证据来源 |
| URL 资料 | URL 智能采集与导入链路 | 作为指定来源和知识资料入口 |
| 证据与引用 | 检索结果中的证据上下文 | 扩展为可追踪的证据卡片 |
| 审核与风险 | `ArticleReview`、`ArticleRiskScan`、风险门禁 | 接入质量检查和人工审核阶段 |
| 内容组 | `ContentGroup`、`ContentVariant` | 作为主文章与各平台版本的归属容器 |
| WordPress 发布 | 现有发布器、分发日志和重试机制 | 继续作为正式发布通道 |
| 队列执行 | `ProcessGeoFlowTaskJob`、`WorkerExecutionService` | 逐步拆成阶段任务，旧流程保留回退 |
| 关键词与标题 | `KeywordLibrary`、`TitleLibrary` | 继续使用，并逐步增强为选题资产 |

### 3.2 改造原则

1. 不重写已有发布、知识检索和审核能力，通过适配器接入新管线。
2. 不把所有步骤继续塞进 `WorkerExecutionService`，新能力按阶段拆分。
3. 每个阶段先保存输入、输出和状态，再推进下一阶段。
4. 自动模式只是自动确认阶段结果，不单独维护另一套生成逻辑。
5. 任何外部调用都必须可超时、可失败、可重试，不能阻断已完成阶段。
6. 新链路受功能开关控制，可按任务或站点逐步启用。

## 4. 目标架构

### 4.1 核心领域对象

建议新增以下对象。最终命名可在第一迭代的技术设计中确认。

| 对象 | 主要职责 |
| --- | --- |
| `ContentProduction` | 一次完整内容生产项目，保存模式、主题、语言、目标站点、规则版本和当前阶段 |
| `ContentStageRun` | 保存每个阶段的输入、输出、状态、耗时、模型、错误和重试次数 |
| `ContentEvidence` | 保存知识库、URL、外部研究获得的证据片段、来源、时间和可信度 |
| `ContentBrief` | 保存受众、意图、观点、必须覆盖内容、禁用内容和引用要求 |
| `ArticleVersion` | 保存大纲、初稿、修复稿、审核稿等版本，避免直接覆盖文章 |
| `QualityReport` | 保存结构、事实、引用、语言、SEO/GEO、重复度等检查结果 |
| `WritingRule` / `WritingRuleVersion` | 保存可复用且不可变的写作规则版本 |
| `ArticleType` | 保存博客、指南、清单、比较、新闻等文章类型要求 |
| `ContentVariantVersion` | 保存各平台改写历史，支持审核、回退和重新生成 |

`Article` 仍是最终可发布内容；`ContentProduction` 负责生产过程；`ContentGroup` 负责主文章与渠道版本的关系。

生产状态不得继续塞入 `Article.status`。建议分别使用：

- 项目状态：`draft`、`queued`、`running`、`waiting_input`、`waiting_review`、`failed`、`completed`、`cancelled`；
- 阶段状态：`pending`、`running`、`succeeded`、`failed`、`skipped`、`waiting_input`、`cancelled`。

所有状态转换集中在编排服务中，使用事务和行锁保护，不能由控制器或队列任务随意改写。

### 4.2 服务边界

建议将新流程拆为以下服务：

- `ContentProductionOrchestrator`：判断下一阶段、推进状态、处理暂停与回退；
- `ResearchService`：聚合知识库、URL 资料和可选外部研究；
- `ContentBriefService`：形成写作简报；
- `TitleProposalService`：生成和评估标题候选；
- `OutlineGenerationService`：生成可编辑的大纲候选；
- `SectionDraftingService`：按大纲分段生成正文；
- `ArticleAssemblyService`：组装正文、摘要、FAQ 和元数据；
- `QualityGateService`：执行确定性规则和模型检查；
- `TargetedRepairService`：仅修复失败项目，避免全文无差别重写；
- `PlatformVariantService`：按平台规则生成内容变体；
- `PublicationCoordinator`：调用现有 WordPress 和分发能力，并保证幂等。

### 4.3 队列策略

当前整篇文章由一个长任务完成，后续逐步改为“一个阶段一个任务”：

- 每个任务只处理一个 `ContentStageRun`；
- 阶段完成后提交事务，再派发下一阶段；
- 分段写作可并行，但必须在全部成功后组装；
- 每个阶段保存输入哈希、输出、模型、规则版本、尝试次数、耗时和错误；
- 每个阶段使用唯一业务键、数据库唯一约束和事务内行锁，防止重复消费；
- 重试不覆盖成功输出；
- 超时、模型错误和资料错误分别记录；
- 生产项目支持“从失败阶段继续”，不需要从头生成。

AI、SERP 和发布等外部调用不得放在长事务中；后续队列必须在事务提交后派发。Laravel 队列自动重试与现有业务重试只能选择一套作为主机制，避免同一失败被双重重试。队列的 `retry_after` 必须大于最长任务超时时间。

## 5. 迭代计划

以下顺序以小步可验收为原则。每个迭代都应独立合并、部署和回滚。

### 迭代 0：冻结契约与建立新链路开关

目标：先明确状态、数据边界和回退方式，不改变用户现有生成体验。

交付内容：

- 定义生产模式、阶段、状态和失败类型；
- 定义各阶段输入输出结构；
- 增加新内容管线功能开关；
- 明确旧 `WorkerExecutionService` 与新管线的适配边界；
- 补充架构决策记录和状态流转图；
- 建立测试数据工厂和生产管线测试基类。

验收：

- 默认仍走旧生成流程；
- 开关关闭时现有任务、文章和发布行为不变；
- 阶段状态和输出结构有自动化契约测试；
- 没有不可逆数据库变更。

### 迭代 1：生产项目与阶段状态

目标：建立可观察、可恢复的生产过程骨架。

交付内容：

- 新增 `ContentProduction`、`ContentStageRun` 及必要索引；
- 新增生产编排器和阶段任务基类；
- 支持从主题手动创建一个生产项目；
- 管理端提供项目列表、详情、阶段时间线、错误和重试入口；
- 记录创建人、站点、模式、语言、目标平台和关联任务。

验收：

- 可以创建一个仅包含空阶段的生产项目；
- 每次阶段状态变化都有时间、操作者和错误记录；
- 同一失败阶段重复点击不会创建多个并行执行；
- 未授权用户不能查看或操作其他范围的项目。

### 迭代 2：研究与证据中心

目标：先解决“依据什么写”，再开始生成正文。

交付内容：

- 新增 `ContentEvidence`；
- 接入现有知识库向量检索；
- 接入 URL 导入资料；
- 支持人工增删证据和标记“必须引用/仅供参考/禁用”；
- 保存来源 URL、标题、采集时间、片段和可信度；
- 保存证据内容快照，不能只保存知识片段 ID；
- 研究失败时允许人工补充资料后继续。

首期暂不依赖 SERP，外部搜索作为后续增强。

验收：

- 一个主题可以检索并保存知识库证据；
- URL 资料可以进入同一证据列表；
- 证据可追溯到原始来源；
- 没有证据时系统明确提示，不能伪造引用；
- 断网环境下仍可使用本地知识库完成研究。

### 迭代 3：内容简报、标题和大纲

目标：让用户在写正文前确认内容方向。

交付内容：

- 生成可编辑的内容简报；
- 生成多个标题候选并支持自定义标题；
- 生成至少两个可对比的大纲候选；
- 支持 H2/H3 编辑、排序、删除和重新生成单个节点；
- 保存选择记录和版本；
- 向导模式在每个关键节点等待确认。

验收：

- 标题和大纲必须基于主题、文章类型、规则和证据；
- 所有输出均为简体中文；
- 用户返回上一步修改后，后续阶段被标记为需要重新生成；
- 已确认版本不会被后台任务静默覆盖。

### 迭代 4：分段写作与文章组装

目标：生成第一篇可读、可编辑、可恢复的完整中文文章。

交付内容：

- 按大纲为每个章节建立独立写作阶段；
- 支持章节级重试和人工重写；
- 组装正文、摘要、FAQ、元标题和元描述；
- 新增 `ArticleVersion`，保存初稿与组装稿；
- 增加中文输出约束和语言检测；
- 最终内容同步到 `Article`，但默认仍为草稿。

验收：

- 单个章节失败不丢失其他成功章节；
- 重新生成一个章节不会改写其他章节；
- 正文、标题、摘要和 FAQ 不夹杂无意义英文说明；
- 生成结果符合选择的篇幅范围；
- 同一阶段重试不会产生重复文章。

### 迭代 5：质量门禁与定向修复

目标：将“生成完成”改为“通过质量检查后完成”。

交付内容：

- 新增 `QualityReport`；
- 接入现有风险扫描与审核模型；
- 增加语言、结构、长度、重复、敏感词、引用完整性检查；
- 增加事实声明与证据覆盖检查；
- 仅对失败项目执行定向修复；
- 质量检查与人工审核结果统一展示。

首期质量门禁建议分两级：

- 阻断项：非中文、空章节、危险内容、引用伪造、发布字段缺失；
- 警告项：关键词覆盖、段落长度、FAQ 数量、风格偏差。

验收：

- 阻断项未通过时不能发布；
- 每条问题显示位置、原因、严重程度和修复结果；
- 修复前后均保留版本；
- 超过修复次数后转人工处理，不进入无限循环。

### 迭代 6：内容生产工作台与可视化创作向导

目标：把迭代 1—5 已经形成的后台能力整合为一套普通用户能够理解、操作和恢复的内容生产前端。

交付内容：

- 建立统一内容生产工作台，首屏展示“可视化 AI 创作、批量自动创作、根据 SERP 创作、模板 AI 创作”四种入口；
- 首期完整开放可视化 AI 创作；尚未完成的入口显示能力说明、前置条件和明确的“即将开放”状态，不能伪装为可用；
- 建立多步骤创作向导：主题与平台 → 文章类型与资料 → 主次关键词 → 标题 → 结构与篇幅 → 大纲 → 额外功能 → 生成与质量检查；
- 复用生产项目和阶段状态，支持保存草稿、退出后继续、返回上一步、重新生成当前节点和查看版本；
- 建立生产进度中心，展示研究、生成、组装、质量检查和修复的实时状态、失败原因及可执行的下一步；
- 整合章节编辑器、证据引用、质量问题定位、定向修复、修复前后对比和文章预览；
- 统一加载、空数据、失败、重试、等待输入、等待审核和完成状态；
- 表单面向普通用户使用清晰字段和合理默认值，JSON 只保留在高级配置或调试视图；
- 完成桌面、平板和手机端基础响应式适配，并保持现有权限、功能开关和旧链路回退能力。

前端入口与后端能力的对应关系：

| 前端模式 | 首期状态 | 依赖能力 |
| --- | --- | --- |
| 可视化 AI 创作 | 完整开放 | 迭代 1—5 |
| 批量自动创作 | 展示并受开关控制 | 迭代 7—8 |
| 根据 SERP 创作 | 展示并受开关控制 | 迭代 11 |
| 模板 AI 创作 | 提供基础编辑器入口，助手逐步开放 | 迭代 7、11 |

验收：

- 用户可以从首页创建生产项目，并在退出后回到正确步骤继续；
- 前后切换不丢失已保存内容，修改上游输入时明确提示并失效相关下游版本；
- 用户可以单独重试失败章节或选中质量问题进行修复，不需要整篇重做；
- 向导模式和自动模式使用相同的阶段名称、状态含义和质量结果；
- 不可用能力有明确状态，不出现点击后无响应、伪进度或静默失败；
- 桌面、平板和手机端可以完成核心创建、查看进度与审核操作；
- 页面不泄露密钥，不绕过授权，不直接渲染未经处理的外部 HTML。

### 迭代 7：写作规则与文章类型版本化

目标：把散落在任务和提示词中的配置沉淀为可复用资产。

交付内容：

- 新增写作规则、规则版本和文章类型管理；
- 支持语言、国家地区、语气、人称、篇幅、结构、引用、链接、FAQ、CTA 等配置；
- 支持关联知识库、品牌资料和敏感词库；
- 生产项目保存规则快照，后续修改规则不影响历史项目；
- 提供预设规则和自定义规则；
- 规则表单使用普通字段，JSON 仅作为底层存储或高级视图。

验收：

- 同一规则可重复用于多篇文章；
- 规则更新后历史文章可复现；
- 冲突配置在提交前给出明确提示；
- 自动模式和向导模式使用相同规则解释器。

### 迭代 8：标准自动模式与每日任务

目标：让成熟的人工流程转为每日自动生产。

交付内容：

- 将现有 `Task`、`TaskSchedule` 适配到新生产项目；
- 支持标准模式自动通过标题和大纲节点；
- 提供每日数量、并发、模型、失败策略和草稿/发布策略；
- 支持任务暂停、恢复、取消和从失败阶段继续；
- 提供任务级成本、耗时和成功率统计；
- 调度增加防重入、单实例执行、站点时区、每日数量和预算上限；
- 保留旧生成链路回退开关。

验收：

- 定时任务每天按配置创建生产项目；
- 同一天重复触发不会重复创建同一选题；
- 失败任务不会阻塞其他任务；
- 多实例部署时同一计划只会被一个调度器执行；
- 默认只生成 WordPress 草稿，自动发布需单独开启；
- 可以一键切回旧流程。

### 迭代 9：WordPress 发布闭环

目标：完成“生产—审核—发布”的可靠闭环。

交付内容：

- 通过 `ContentGroup` 关联主文章；
- 复用现有 WordPress 发布器和分发日志；
- 增加特色图、分类、标签、摘要和规范链接检查；
- 保存 WordPress 文章 ID、URL、发布时间和发布版本；
- 支持发布草稿、定时发布、立即发布和失败重试；
- 发布后内容修改必须形成新版本。

验收：

- 同一文章重复执行发布只产生一个 WordPress 文章；
- 发布失败可安全重试；
- 发布记录能追溯到生产项目、文章版本和审核人；
- 未通过质量门禁或人工审核的内容不能正式发布。

### 迭代 10：多平台改写与审核

目标：将 WordPress 主文章改写为七类中文内容平台版本。

执行拆分：

- 10A：先完成手动主文章进入内容组、七平台按规则改写、单平台重新生成、事实硬指标检查和不可变版本历史；
- 10B：补齐平台版本人工编辑、审核流、批量导出以及更完整的质量检查；
- 自动发布不纳入 10A/10B，待各平台授权方式和稳定性验证后逐个平台开放。

交付内容：

- 基于现有 `ContentVariant` 生成百家号、企鹅号、网易号、搜狐号、头条号、知乎和公众号版本；
- 新增平台规则和变体版本历史；
- 支持单个平台重新生成、编辑、审核和导出；
- 支持平台标题、摘要、正文、标签和图片要求；
- 明确显示“待生成、生成中、待审核、可发布、已发布、失败”状态；
- 自动分发在各平台授权和稳定性验证后逐个平台开放。

验收：

- 八个内容版本归属于同一个 `ContentGroup`；
- 平台改写保留事实与核心观点，但文风和结构符合平台规则；
- 修改某个平台版本不影响主文章和其他平台；
- 平台发布失败不影响 WordPress 和其他平台状态。

### 迭代 11：编辑器助手、SERP 与运营增强

目标：补齐高价值增强功能，不阻塞主链路上线。

交付内容：

- 编辑器中的扩写、改写、标题、描述、段落、FAQ、大纲等助手；
- SERP 研究作为研究阶段的可选证据源；
- 竞争页面对比和内容缺口分析；
- 快速模式和批量模式体验优化；
- 选题、关键词、质量、发布和平台效果仪表盘；
- 为未来与 seo-diagnostic 对接准备只读指标接口。

验收：

- 编辑器助手只修改用户选中的范围；
- SERP 不可用时可降级到知识库和 URL 资料；
- 外部资料有来源和采集时间；
- 运营指标能回溯到具体生产项目和版本。

## 6. 优先级与阶段性范围

## 7. 每个迭代的统一完成标准

每个迭代只有同时满足以下条件才算完成：

- 数据迁移可回滚，常用查询有索引，关系和类型转换明确；
- 只新增前向迁移，不回改已经进入生产的历史迁移；
- 写操作使用请求验证、授权和服务层，不把业务流程堆进控制器；
- 队列任务具有幂等键、超时、失败记录和有限重试；
- 外部调用有超时、错误分类和降级策略；
- 核心状态流转有功能测试；
- 关键服务有单元测试；
- 至少覆盖一次失败、重试和重复执行场景；
- 管理端可看到当前状态、错误和下一步操作；
- 不在日志、数据库明文或界面暴露密钥；
- 新功能受开关控制，旧流程仍可回退；
- 文档、配置示例和验收记录同步更新。

## 8. 测试策略

### 8.1 自动化测试

- 状态机：合法与非法阶段跳转；
- 幂等性：重复派发、重复回调、重复发布；
- 事务：阶段成功保存后才派发下一任务；
- 知识检索：本地证据、无结果和离线场景；
- 语言：中文比例、英文残留和字段完整性；
- 质量门禁：阻断、警告、修复和人工接管；
- 发布：WordPress 成功、超时、重复和部分失败；
- 变体：平台独立版本和单平台重试；
- 权限：项目、规则、审核和发布权限；
- 前端：向导前后切换、草稿恢复、错误重试、不可用能力提示和响应式布局；

### 8.2 端到端验收样本

固定维护至少五组回归样本：

1. 仅企业知识库；
2. 知识库加 URL 资料；
3. 资料不足，需要人工补充；
4. 长文章，包含 FAQ、内链和引用；
5. WordPress 主文加七个平台版本。

每组样本保存输入、证据、规则、预期结构和质量阈值，避免只凭主观阅读验收。

## 9. 上线顺序与回退

1. 开发环境启用新管线，旧任务不迁移；
2. 选择一个人工主题进行向导模式试运行；
3. 选择一个站点只生成 WordPress 草稿；
4. 连续通过回归样本后开放标准自动模式；
5. 自动发布先按单站点、低频率开启；
6. 多平台按“生成与审核”先上线，自动发布逐个平台开启；
7. 发生严重问题时关闭新管线开关，新任务回到旧流程；已开始的新项目保留状态供恢复。

禁止在同一次上线中同时启用新生产管线、自动发布和全部平台分发。

## 10. 关键指标

上线后至少记录：

- 各阶段成功率、平均耗时和重试次数；
- 单篇文章模型调用次数与成本；
- 中文输出合格率；
- 证据覆盖率和引用有效率；
- 质量门禁首次通过率与修复成功率；
- 人工修改比例和审核退回原因；
- WordPress 重复发布数，目标为 0；
- 每个平台生成、审核和发布成功率；
- 从选题到草稿、从草稿到发布的总周期。

## 11. 下一开发批次

迭代 0—11 已完成首轮实现，下一开发批次进入整体验收、生产灰度和真实业务数据校准。

建议按以下顺序交付：

1. **失败阶段续跑（已完成）**：失败任务重新入队后复用已有证据、已确认标题和大纲、成功章节、文章组装及质量检查结果；
2. **运行统计（已完成）**：任务列表展示最终成功数、失败数、成功率、平均耗时和最近失败原因；
3. **明确不纳入当前范围**：包月模型场景暂不开发 Token 成本账本、主备模型和自动故障切换。
4. **生产灰度**：默认保持 WordPress 草稿，先由超级管理员小范围验证手动创作、多平台改写、审核和发布闭环；确认日志与版本记录后再开放自动任务。

## 13. 下一轮内容智能增强

- **迭代 21A（已完成，待环境验证）**：标题和大纲由内容方向 AI 优先生成，用户仍可编辑、选择并保存；模型或 JSON 输出异常时明确降级为规则候选。
- **迭代 21B（已完成，待环境验证）**：研究中心可选择 AI 联网检索；只接受带 URL 的可追溯引用，并将研究摘要用于标题与大纲的选题补充。联网引用不是文章证据，网页正文必须经过 URL 智能采集并由用户加入证据中心后才能用于事实写作和引用门禁。未配置支持联网检索的模型时，保留 URL / 知识库研究流程并提示降级原因。
- **迭代 21C（已完成，待环境验证）**：文章生成完成后可提交“修改意见”。系统以当前文章版本为源稿创建独立的 AI 修订请求和新文章版本，保留原始意见、规则快照、模型、变更说明、失败信息与质量报告；修订结果不会覆盖历史版本，并会自动回到草稿/待审核状态及重新质量检查。
